# WindyTranslator 小工具 Agent 接入规范

## 0. 任务边界

本文件是让 Agent 将**已有的翻译辅助工具**接入 WindyTranslator 的执行规范。

- 工具由 `tools/<id>/manifest.json` 发现并启动。
- 主程序只负责发现、传入已声明的参数、启动独立进程和显示 CLI 输出。
- GUI 工具保留自己的窗口；主程序不会嵌入、接管或等待它关闭。
- 首选交付物是源码工具目录，不是完整 Python 环境、`build/`、`dist/`、缓存或测试产物。
- 改造目标是“增加启动参数并保留原行为”，不是把工具业务逻辑重写进 WindyTranslator。

除非用户明确要求，Agent 不得修改 `core/tools/manager.py`、`ui/tools_panel.py`、主程序任务流程或其他工具来迁就一个新工具。

## 1. 不可违反的规则

1. 每个工具必须位于 `tools/<id>/`，且目录名与 Manifest 的 `id` 完全一致。
2. 每个工具必须提供 UTF-8 编码的 `manifest.json` 和实际存在的入口文件。
3. `id` 只能使用 ASCII 字母、数字和下划线：`^[A-Za-z0-9_]+$`。
4. `entry`、`working_directory`、`resources` 必须是工具目录内的相对路径；禁止绝对路径、`..`、软链接逃逸和任意 shell 命令。
5. 工具必须使用参数列表接收值。禁止 `shell=True`、命令模板、环境变量拼接和依赖启动时的当前目录。
6. 工具独有 Python 依赖必须随工具放在 `vendor/`。禁止在启动时 `pip install`、联网下载或修改宿主依赖。
7. 工具源码不得导入 WindyTranslator 的 `app`、`ui`、`core`、`scripts` 作为运行依赖。需要的少量通用函数应复制为工具自身源码。
8. GUI 工具不传启动参数时必须仍可按其原本方式启动；启动参数只能预填或自动加载已有流程。
9. 只保留工具运行必需的源码、资源、配置、资料和许可证。禁止提交 `__pycache__/`、`.pytest_cache/`、`build/`、`dist/`、日志和临时导出文件。
10. 任何文件写入、覆盖或删除必须由工具自己的 UI 或显式命令完成；启动工具本身不得产生数据修改。

## 2. Agent 执行流程

开始改造前，按顺序完成以下事项：

1. 阅读现有工具入口、参数解析、资源定位和保存逻辑。
2. 确认它是 `gui` 还是 `cli`：有独立 Tk/Qt 等窗口用 `gui`；只输出结果用 `cli`。
3. 列出工具真正需要的输入，并只映射到第 4 节允许的参数类型。
4. 创建 `tools/<id>/`，移入或复制最小运行源码和资源；不要复制发布垃圾。
5. 以 `Path(__file__).resolve().parent` 为基准定位工具自己的配置、资料和资源。
6. 添加 `manifest.json`，为 GUI 入口增加 `argparse` 参数预填；不重写原 GUI。
7. 按第 7 节命令验证发现、入口和原有功能。

遇到不满足本规范的需求时，停止并说明限制，不要暗中扩展 Manifest、增加隐藏 UI、自动安装依赖或修改宿主。

## 3. 固定目录契约

```text
tools/
  <id>/
    manifest.json
    entry.py               # 工具的入口文件
    ...工具源码...
    resources/             # 外部 EXE、DLL 或其他二进制资源
    vendor/                # 仅工具独有的 Python 依赖
```

`tools/` 只扫描一级子目录。没有 `manifest.json` 的目录不会作为工具启动。Manifest 无效或入口/资源缺失时，工具不会变为可启动状态，页面显示“状态检查未通过”。

## 4. Manifest v1 契约

所有字段均应写出，不依赖隐式默认值。

```json
{
  "manifest_version": 1,
  "id": "example_tool",
  "name": "示例工具",
  "version": "1.0.0",
  "author": "作者名",
  "description": "一句话说明工具处理什么。",
  "category": "gui",
  "runtime": "host_python",
  "entry": "entry.py",
  "working_directory": ".",
  "resources": [],
  "arguments": []
}
```

| 字段 | 规则 |
| --- | --- |
| `manifest_version` | 必须为整数 `1`。 |
| `id` | 必须等于工具目录名，且符合第 1 节的字符限制。 |
| `name` / `version` / `author` / `description` | 工具信息；必须是非空字符串。 |
| `category` | 只能为 `gui` 或 `cli`。 |
| `runtime` | 只能为 `host_python` 或 `exe`。 |
| `entry` | 工具目录内、实际存在的入口文件相对路径。 |
| `working_directory` | 工具目录内的相对路径；通常为 `"."`。 |
| `resources` | 工具目录内的外部资源相对路径数组；文件不存在即状态检查失败。 |
| `arguments` | 参数对象数组；没有参数时必须写 `[]`。 |
| `launch_options` | 可选的固定启动预设数组；存在时取代顶层 `arguments`。 |
| `launch_options_label` | 可选；启动预设下拉框的显示名称，默认为“启动选项”。只能与 `launch_options` 一起使用。 |

不要增加宿主未定义的字段。

## 5. 运行时和依赖

### `host_python`

这是默认且推荐的源码模式。宿主会以子进程运行：

```text
WindyTranslator --run-tool <工具目录> <入口文件> <参数...>
```

工具目录和存在时的 `vendor/` 会加入导入路径，进程工作目录为 Manifest 的 `working_directory`。工具应只依赖标准库、自己的 `vendor/` 和自身目录文件。

### `exe`

将 `runtime` 写为 `exe`，`entry` 指向工具目录内的 EXE。参数仍完全由 `arguments` 定义。EXE 的运行时、DLL 和配置由工具作者负责，仍不得引用工具目录外的隐式文件。

### 资源定位示例

```python
from pathlib import Path

TOOL_ROOT = Path(__file__).resolve().parent
PARSER = TOOL_ROOT / "resources" / "lcf2xml.exe"
CONFIG_DIR = TOOL_ROOT / "配置"
```

禁止以 `os.getcwd()`、主程序目录、用户主目录或固定盘符推导工具资源路径。

## 6. 参数契约

参数对象格式：

```json
{
  "name": "input",
  "flag": "--initial-input",
  "type": "current_game_file",
  "source": "translated/translation_translated.json",
  "required": true,
  "label": "译文 JSON 文件"
}
```

小工具参数由主程序自动提供：

| 类型 | 来源 | 限制 |
| --- | --- | --- |
| `game_path` | 主窗口当前选择的游戏目录，或其 `source` 子路径。 | `source` 可选；存在时必须是安全相对路径。 |
| `current_game_file` | 当前游戏对应工作目录中的 `source` 文件。 | `source` 必须是非空、安全相对路径；禁止绝对路径和 `..`。 |
| `fixed` | Manifest 的 `value`。 | `value` 必须明确写出，不能包含 `source`。 |

需要游戏上下文的必需参数在未选择有效游戏目录时，会优先显示“请先选择一个有效的游戏目录”。游戏目录已选择但目标 JSON/CSV 缺失时，工具入口必须自行显示清晰的缺失文件错误。

`current_game_file` 示例：

```json
{
  "name": "translated_json",
  "flag": "--translated-json",
  "type": "current_game_file",
  "source": "translated/translation_translated.json",
  "required": true,
  "label": "译文 JSON 文件"
}
```

`game_path` 子目录示例：

```json
{
  "name": "translated_dir",
  "flag": "--initial-translated-dir",
  "type": "game_path",
  "source": "StringScripts",
  "required": true
}
```

`fixed` 示例：

```json
{
  "name": "parser",
  "flag": "--initial-parser",
  "type": "fixed",
  "value": "resources/lcf2xml.exe"
}
```

### 启动预设

同一工具有多种固定启动方式时，使用 `launch_options`。每个选项拥有完整参数集，工具页面默认选中数组第一项；选项不合并顶层参数，也不保存用户选择。可用顶层 `launch_options_label` 为下拉框命名，例如“统计内容”或“校对来源”。

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `launch_options` | 否 | 非空数组；存在时取代顶层 `arguments`。 |
| `id` | 是 | 选项标识；仅限 ASCII 字母、数字和下划线，且同一工具内不可重复。 |
| `name` | 是 | 下拉框显示的非空名称。 |
| `arguments` | 是 | 非空参数数组；每个参数遵循第 6 节的参数契约。 |

```json
{
  "launch_options": [
    {
      "id": "json",
      "name": "JSON 译文",
      "arguments": [
        {
          "name": "input",
          "flag": "--initial-input",
          "type": "current_game_file",
          "source": "translated/translation_translated.json",
          "required": true
        }
      ]
    }
  ]
}
```

定义 `launch_options` 时，顶层 `arguments` 必须为空或省略。

## 7. GUI 与 CLI 入口模板

### GUI：保留原行为，仅预填

```python
import argparse

def main() -> None:
    parser = argparse.ArgumentParser()
    parser.add_argument("--initial-project")
    parser.add_argument("--initial-input")
    args = parser.parse_args()

    app = ExistingApp(
        initial_project=args.initial_project,
        initial_input=args.initial_input,
    )
    app.mainloop()

if __name__ == "__main__":
    main()
```

`initial_*` 为空时，必须保留原工具自己的文件选择和正常启动流程。值完整时可以在 GUI 创建后通过 `after_idle` 自动加载，但不得在创建根窗口前做 GUI 操作。

### CLI：输出可读结果和退出码

```python
import argparse
from pathlib import Path

def main() -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("--input", required=True)
    args = parser.parse_args()
    input_path = Path(args.input)
    if not input_path.is_file():
        print(f"输入文件不存在：{input_path}")
        return 2
    print("检查完成。")
    return 0

if __name__ == "__main__":
    raise SystemExit(main())
```

`category: "cli"` 的 stdout 和 stderr 会显示在小工具日志。`category: "gui"` 的输出不会在主窗口转发，因此 GUI 工具必须用自己的窗口显示错误。

## 9. 验收命令

在仓库根目录执行；将 `<id>` 和 `<entry>` 替换为实际值。

```powershell
# 入口可编译
python -m compileall -q tools\<id>

# Manifest 可被发现，且没有诊断
python -c "from core.tools import ToolManager; tools, diagnostics = ToolManager('tools').discover(); print([tool.id for tool in tools]); print(diagnostics)"

# 源码宿主可把参数交给入口；--help 不应创建 GUI 或修改文件
python main.py --run-tool tools\<id> tools\<id>\<entry> --help
```

提交前，Agent 必须确认：

- `manifest.json` 可解析，工具显示在“小工具”列表中；
- `id`、目录、入口和资源路径全部匹配；
- 未选游戏时，游戏依赖工具显示正确的游戏目录错误；
- 选中游戏后，传入路径包含中文和空格仍能正常工作；
- 不传启动参数时，原 GUI 行为未被破坏；
- CLI 成功为 `0`，输入错误为非零退出码；
- 没有新增自动安装、网络下载、shell 拼接或主程序耦合；
- 没有提交构建产物和缓存。

## 10. 禁止的“修复”

以下情况必须修工具自身，不能修改宿主绕过：

- 入口不能接收 Manifest 中声明的 `flag`；
- GUI 依赖旧发布目录、固定盘符或主程序内部模块；
- 工具缺少第三方包、EXE、DLL、配置或资料；
- 译文 JSON/CSV 不存在、格式不正确或编码不正确；
- 工具关闭、保存或异常处理与自身 GUI 生命周期有关。

Manifest 仅是启动契约，不是执行任意命令的配置文件。任何需要超出本规范的新能力，先向用户说明并取得明确授权。
